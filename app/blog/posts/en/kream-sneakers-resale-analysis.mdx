An Operations Analyst project on Kream sneakers resale: ingest trade history, model it as a star schema, and report premiums, seasonality, and buy/sell signals in Power BI.

Source code and the Power BI workspace stay private. This page matches the actual model and report pages.

## Problem

Resale decisions need model×size trade frequency, price level, and premium versus retail. A few recent rows on a product page are not enough for seasonality, size premiums, or delivery-type gaps.

## Pipeline overview

```text
Product page (model / size metadata)
        │
        ▼
Trade history collection (per size)
        │
        ▼
CSV per model · size  (+ resume / merge)
        │
        ▼
Validate · normalize dates · sales fact export
        │
        ▼
Power BI star schema (fact_sales + dims)
        │
        ▼
Dashboard pages (overview · price · signals · premium)
```

Collection uses Playwright (CDP) to store size, price, date, and delivery type; merges and validates; then exports into Power BI.

## Data quality rules

| Rule | Why |
| --- | --- |
| Size prefix validation | Keep scroll batches from mixing sizes |
| Completion ratio (≥ 90%) | Judge coverage vs expected volume |
| Relative date → absolute | Normalize “3 hours ago” style dates |
| Dedup on merge / update | Drop duplicates; append only new trades |
| Master product cache | Cache brand, release date, retail, category in `sneakers_info` |

## Data modeling (star schema)

From the live Power BI model:

- **Fact** — `fact_sales` at trade grain (`SKU`, `Size`, `Size Type`, `Price`, `DeliveryType`, `DateKey`)
- **Dimensions** — `dim_product` (Model_No, Name_En/Kr, Brand, Category, Color, IsCollab, Release_Date, Retail_Price), `dim_brand`, `dim_date`
- **Relationships** — `dim_date[DateKey] → fact_sales`, `dim_product → fact_sales`, `dim_brand → dim_product` (plus inactive brand→fact)
- **What-if / disconnected tables** — `Analysis Period`, `Profit Target %`, `Sales or Qty`, `Signal_Toggles` (e.g. BB Touch)

```text
dim_brand ──► dim_product ──► fact_sales
dim_date    ─────────────────► fact_sales

disconnected: Analysis Period · Profit Target % · Sales or Qty · Signal_Toggles
```

Key measures include `%Average Premium`, `Daily Avg Price`, Bollinger / RSI / Trend buy·sell conditions, and `KREAM Price Forecast`.

## Dashboard

Instead of a public Publish-to-web embed (free-license limit), the report pages are:

1. **Overview** — Total Sales / Quantity / %Average Premium KPIs, sales by date, sales by brand (Jordan · Nike · Adidas lead), category and `IsCollab` slicers, max-premium callout
2. **Price trend** — Brand · Product · Size filters with Daily Avg Price by Date
3. **Signals** — Transaction Quantity vs Avg Price, Bollinger Band Analysis, Analysis Period / Profit Target % what-if inputs, Master Buy·Sell markers
4. **Premium by brand** — %Average Premium by brand, Retail vs Resale bubble (sized by quantity), weekday/weekend premium matrix
5. **Size heatmap** — Size × Brand premium heatmap (MM / US / W-MM), premium over time by DeliveryType

Sample-wide observations:

- About **3M** trades, ~**912bn** KRW sales, ~**59%** average premium
- Sales concentration: Jordan → Nike → Adidas
- Jordan is a clear premium outlier versus retail
- Premium splits further by size, delivery type, and collaboration flag

## DAX / modeling notes

- Prefer relationships for dimension attributes; keep dynamic logic in measures
- `%Average Premium` compares resale price to `dim_product[Retail_Price]`
- Bollinger / RSI / Trend signals use fact measures plus what-if parameters for window length and profit target
- `Sales or Qty` switches the value axis on shared visuals

```dax
%Average Premium =
DIVIDE (
    [Daily Avg Price] - SELECTEDVALUE ( dim_product[Retail_Price] ),
    SELECTEDVALUE ( dim_product[Retail_Price] )
)
```
