An Operations Analyst project on Kream sneakers resale: a CDP-based trade collector that resumes, updates, and validates per size, then feeds a star schema and Power BI dashboards for premiums, seasonality, and buy/sell signals.

Source code and the Power BI workspace stay private. This page documents the collector design, data rules, model, and report pages.

## Problem

Resale decisions need model×size trade frequency, price level, and premium versus retail. A few recent rows on a product page are not enough for seasonality, size premiums, or delivery-type gaps — and long infinite-scroll histories cannot be scraped once and forgotten. Collection has to survive rate limits, session expiry, and partial runs.

## Collection engine

The core is a **stateful collector**, not a one-shot crawl. Playwright attaches to an already-logged-in Chrome via CDP (`localhost:9222`), then walks each product through:

```text
Queue / product page
        │
        ▼
Identify model · cache or analyze sizes (expected volume)
        │
        ▼
Collect missing sizes only (95% = complete)
        │
        ▼
Per-size scroll loop → CSV (Size, Price, Date, DeliveryType)
        │
        ▼
Merge (+ SKU) → sales fact → Power BI
```

Entry points: interactive single-product run, batch queue processor, and a queue adder that pulls model / URL / name from the open tab.

### Per-size collection modes

| Mode | When | Behavior |
| --- | --- | --- |
| Full | No final CSV | Newest-first scroll into a temp `_W` file; rename on success |
| Update | Final CSV exists | Collect only new trades; stop on ≥80% batch overlap; prepend uniques |
| Resume | Interrupted run | Keep `_W` / `_W_reverse` if large enough; else start fresh |
| Bottom gap fill | Top is current, oldest missing | Oldest-first scroll to close the hole |
| Reverse-append | Resume from `_W` | Oldest-first until overlap with prior oldest date |

Completion is not a raw row count. The engine treats a size as done when it hits the target, reaches ~90% of expected volume, or ends on a natural batch boundary (not a multiple of 50) near that threshold — so soft-bans are not mistaken for “finished.”

### Resilience built into the loop

| Signal | Response |
| --- | --- |
| Soft-ban (no new rows) | Progress-based no-change thresholds → exponential backoff → reload → retry remaining sizes |
| Session expiry | Detect login URL/modal → re-login → retry current size |
| Scroll stuck (too fast) | Scroll-up unstick (capped retries) → error if still stuck |
| Wrong-size rows | JS size-prefix check → `CORRUPTED` abort |
| Bad dates | Filter invalid date fields before write |
| Size analysis quality | Reject identical volumes, duplicate keys, mostly-zero volumes |
| Very high volume | Skip sizes above a safe volume cap |

Batch mode runs the same pipeline unattended: read `scrape_queue.csv`, collect missing sizes, merge on success, remove from queue, notify on soft-ban / skip / batch summary.

## Data quality rules

| Rule | Why |
| --- | --- |
| Size prefix validation | Keep scroll batches from mixing sizes |
| Completion ratio (≥ 90% / 95%) | Soft-complete vs “already collected” for missing-only |
| Relative date → absolute | Normalize “3 hours ago” using file mtime at fact export |
| Dedup on merge / update | Drop duplicates; append only new trades |
| Master product cache | Brand, release date, retail, size distribution in `sneakers_info` |
| Dual size keys | Disambiguate same KR mm with different US labels (e.g. `250_W8`) |

## From CSV to fact

Grain is always **one trade**.

- Per size: `CSV/{MODEL}/{MODEL}_{size}.csv`
- Per model: `{MODEL}_merged.csv` (+ `SKU`)
- Cross-model: `sales_fact.csv` (`SKU`, `Size`, `Price`, `Date`, `DeliveryType`) — incremental append by default, full rebuild optional

## Data modeling (star schema)

In Power BI:

- **Fact** — `fact_sales` at trade grain (`SKU`, `Size`, `Size Type`, `Price`, `DeliveryType`, `DateKey`)
- **Dimensions** — `dim_product` (Model_No, Name_En/Kr, Brand, Category, Color, IsCollab, Release_Date, Retail_Price), `dim_brand`, `dim_date`
- **Relationships** — `dim_date[DateKey] → fact_sales`, `dim_product → fact_sales`, `dim_brand → dim_product` (plus inactive brand→fact)
- **What-if / disconnected** — `Analysis Period`, `Profit Target %`, `Sales or Qty`, `Signal_Toggles`

```text
dim_brand ──► dim_product ──► fact_sales
dim_date    ─────────────────► fact_sales

disconnected: Analysis Period · Profit Target % · Sales or Qty · Signal_Toggles
```

Key measures: `%Average Premium`, `Daily Avg Price`, Bollinger / RSI / Trend buy·sell conditions, `KREAM Price Forecast`.

## Dashboard

Instead of a public Publish-to-web embed (free-license limit), the report pages are:

1. **Overview** — Total Sales / Quantity / %Average Premium KPIs, sales by date, sales by brand (Jordan · Nike · Adidas lead), category and `IsCollab` slicers
2. **Price trend** — Brand · Product · Size filters with Daily Avg Price by Date
3. **Signals** — Quantity vs Avg Price, Bollinger Band Analysis, what-if period / profit target, Master Buy·Sell markers
4. **Premium by brand** — %Average Premium by brand, Retail vs Resale bubble, weekday/weekend premium matrix
5. **Size heatmap** — Size × Brand premium heatmap (MM / US / W-MM), premium over time by DeliveryType

Sample-wide observations:

- About **3M** trades, ~**912bn** KRW sales, ~**59%** average premium
- Sales concentration: Jordan → Nike → Adidas
- Jordan is a clear premium outlier versus retail
- Premium splits further by size, delivery type, and collaboration flag

## DAX / modeling notes

```dax
%Average Premium =
DIVIDE (
    [Daily Avg Price] - SELECTEDVALUE ( dim_product[Retail_Price] ),
    SELECTEDVALUE ( dim_product[Retail_Price] )
)
```

- Prefer relationships for dimension attributes; keep dynamic logic in measures
- Bollinger / RSI / Trend signals combine fact measures with what-if window and profit target
- `Sales or Qty` switches the value axis on shared visuals
