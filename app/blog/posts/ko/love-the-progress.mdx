진행 상태가 어떻게 저장·갱신·제공되는지를 보여주는 제품형 프로젝트입니다. UI 장식보다 스키마 명확성과 백엔드 규칙에 초점을 둡니다.

## Product intent

스냅샷만이 아니라 시간에 따른 의미 있는 진행을 추적합니다. 데이터 모델은 “무엇이 바뀌었는지”와 “왜 그것이 중요한지”를 쉽게 조회할 수 있어야 합니다.

## Database schema (draft)

엔티티와 관계를 여기에 정리합니다.

```text
users
  └── goals
        └── milestones
              └── progress_events

optional:
  tags / categories
  reflections / notes
  audit_log
```

### Suggested tables

| Table | Purpose | Key fields |
| --- | --- | --- |
| `users` | Account identity | `id`, `email`, `created_at` |
| `goals` | Long-running outcomes | `id`, `user_id`, `title`, `status`, `target_date` |
| `milestones` | Checkpoints on a goal | `id`, `goal_id`, `title`, `sequence`, `completed_at` |
| `progress_events` | Append-only activity | `id`, `goal_id`, `milestone_id?`, `kind`, `value`, `occurred_at` |

명시할 제약:

- Progress events는 **append-only** (수정은 silent edit가 아니라 compensating event)
- Milestone 완료는 파생값이거나, 백엔드에 명확한 규칙으로 명시적 설정
- Foreign key와 cascading 규칙 문서화 (restrict vs cascade)

## Backend logic

API가 강제하는 도메인 규칙:

1. **Create goal** — ownership 검증; 기본 status; 선택적 첫 milestone
2. **Record progress** — goal status 위반 이벤트 거부 (예: archived goals)
3. **Complete milestone** — idempotent 완료; 동일 트랜잭션에서 progress event 발행
4. **Read progress timeline** — `occurred_at` 정렬; goal / kind 필터 지원

트랜잭션 경계 예시:

```text
BEGIN
  insert progress_event
  update milestone.completed_at (if applicable)
  recompute goal status (if all milestones done)
COMMIT
```

## Trade-offs

- Append-only 이벤트는 저장 비용이 들지만 감사와 “love the progress” 스토리텔링이 단순해짐
- Derived status vs stored status: 단일 source of truth를 정하고 문서화
- 사용자가 포기한 goal에 대한 soft delete vs hard delete
